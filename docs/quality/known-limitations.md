# Known Limitations

This page describes constraints visible in the current source. It is not a
deployment certification; use the current CI and release evidence for build,
test, and runtime status.

## 1. Backend scope and scaling

| Limitation | Current behavior | Impact / next step |
|---|---|---|
| Single-node realtime broker | Spring `SimpleBroker` and `PresenceSessionRegistry` are process-local (`server/src/main/java/com/nexachat/config/WebSocketConfig.java`, `server/src/main/java/com/nexachat/presence/PresenceSessionRegistry.java`). | Events and online-session counts do not span backend instances. A multi-node deployment needs shared presence state and a broker relay. |
| Live subscription after member removal | Membership is checked at SUBSCRIBE and again on every `/topic/conversations.{id}` delivery (`StompConversationMembershipOutboundInterceptor` on the client outbound channel). `GroupService` also unregisters that user's topic subscription after the removal transaction commits. | A frame already handed to the broker before the membership delete commits can still arrive. The filter and the broker are single-node. Destinations other than the conversation topic are outside this filter. |
| In-memory rate limits | `RateLimitService` keeps bounded token buckets in the server process. | Budgets reset on restart and are independent across nodes; use a shared store before scaling out. |
| Presence privacy and scope | Presence is sent only to DIRECT peers while the subject's `show_presence` setting is on; groups receive no presence. Hiding one's own state does not hide peers' state from that user. | This is a coarse account-level, one-way control, not per-contact visibility. |
| Presence state | Presence is tracked in the in-memory `PresenceSessionRegistry` and is single-node. | Online state does not span backend instances; a multi-node deployment needs shared presence state. |
| Message search index | Message search uses `public.f_unaccent(m.content)` + `ILIKE` substring matching scoped to a conversation, accelerated by a composite GIN trigram index `idx_msg_conv_content_trgm` on `(conversation_id, f_unaccent(content))` (Flyway V8, `server/src/main/java/com/nexachat/message/MessageRepository.java`). | Conversations with high message volumes benefit from trigram index scans; queries with non-selective search terms still scan matching candidate heap rows. |
| Conversation RAG ("Ask this chat") | Server-side RAG pipeline (`POST /api/v1/conversations/{id}/ask`, Flyway V9) and the Android Ask screen are present (`server/src/main/java/com/nexachat/rag/**`, `android/app/src/main/java/com/nexachat/feature/ask/`, [docs/architecture/rag.md](../architecture/rag.md)). | External embedding calls require user consent and an API key (`NEXACHAT_RAG_EMBEDDING_API_KEY`); live external embedding smoke was not run in CI/audit due to unset API key. Per-conversation AI opt-out (Flyway V13) excludes opted-out authors from retrieval, indexing and cached-answer replay. Aggregate telemetry `/api/v1/rag/stats` is restricted to authorized admin phones (`NEXACHAT_ADMIN_PHONES`). |
| Soft-deleted attachment retention | Deleting a message removes reaction rows and any pin and makes its attachment inaccessible through the deleted message, but keeps attachment metadata and stored bytes. | Storage is not reclaimed automatically by default. Bounded background cleanup is implemented in `RetentionJobRunner` (Job `ATTACHMENTS`), but requires explicit operator enablement (`NEXACHAT_RETENTION_ENABLED=true`, `NEXACHAT_RETENTION_DRY_RUN=false`, and `NEXACHAT_RETENTION_ATTACHMENTS_ENABLED=true`). See [docs/operations/production-runbook.md](../operations/production-runbook.md). |
| Global message sequence | PostgreSQL `BIGSERIAL` values are unique and monotonic globally, not contiguous per conversation (`server/src/main/resources/db/migration/V1__init.sql`). | Sequence gaps are normal; consumers must use ordered cursors, not infer row counts from sequence differences. |
| Access-token revocation | Logout, logout-all, and password change stamp `users.tokens_valid_after` (Flyway V11). REST checks and each STOMP SEND/SUBSCRIBE reject tokens whose `iat` precedes the cutoff; committed revocations also close tracked sockets on the same server process. | A multi-instance deployment does not broadcast socket-close events across servers. Shared realtime/session invalidation is needed before scaling out. Refresh tokens rotate and revoke independently. |
| Phone ownership | Registration uses phone number plus password and does not verify phone ownership with OTP. | The service cannot prove that a registrant controls the number. Adding verification requires an external messaging provider. |
| Phone enumeration | Registration reports `PHONE_EXISTS`; login uses a uniform invalid-credentials response. | An unauthenticated caller can learn whether a phone is registered. Rate limiting reduces, but does not remove, that disclosure. |
| Google-only accounts | With `NEXACHAT_GOOGLE_SIGNUP_ENABLED=true`, `POST /auth/google` can create accounts that have no E.164 phone and no password hash (Google `sub` + verified email only). | Self-service add-phone and set-password flows for these accounts are not implemented yet; unlink is refused with `LAST_SIGN_IN_METHOD`. They delete themselves with an email code sent to the verified address (`POST /users/me/deletion-code`). |
| Cross-origin (CORS) allow-list | CORS and WebSocket handshake origins use an explicit allow-list from `nexachat.security.cors-allowed-origins` (`NEXACHAT_CORS_ALLOWED_ORIGINS`). The default is empty (admitting no cross-origin browser callers, safe for native mobile clients), and wildcard `*` is rejected at startup. Credentials are never enabled. | Deployments serving a web/browser client must configure explicit allowed origins in `NEXACHAT_CORS_ALLOWED_ORIGINS`. |
| Call feature | Call signaling, ICE configuration, server call history and the Android call UI are shipped (`server/call`, `android/.../call`); the live call E2E (`tools/e2e/calls/call_e2e.py`) passes and on-device screens are captured in `docs/media/screens/`. | Audio has not been verified between two real devices (see the call-audio row below); the signaling/UI path is otherwise verified. |
| Call infrastructure | Call state and STOMP delivery use the single-node in-memory registry and `SimpleBroker` (`docs/architecture/calls.md`). | Multiple server instances need shared call coordination and a broker relay. |
| Call NAT traversal | The default ICE configuration has public STUN only and no TURN. | Strict NAT or mobile networks may not establish media; a shared LAN/Wi-Fi path is the expected demo environment. |
| Call scope | Only DIRECT conversations with exactly two members can call; calls are audio-only. | Group calls are out of scope. |
| Call delivery while offline | Token registration and server FCM dispatch exist with OAuth2 service-account authentication (`DefaultFcmPushService`, `GoogleHttpFcmGateway`, `FcmTokenProvider`), but live push delivery requires an external Firebase project and credentials (not in repository). Without live FCM, an offline callee receives no ring notification; the ring expires as a missed call and leaves a history row plus a localized chat line. | External Firebase configuration and `google-services.json` are required for push delivery to backgrounded or stopped devices. |
| Call audio path | Audio media is negotiated by the Android client and depends on WebRTC availability on the device. The live E2E and on-device run verified signaling, SDP/ICE relay, mute/speaker routing and teardown, but not an audio stream between two WebRTC endpoints. | A missing or failed WebRTC stack degrades the call; a real two-device audio test is still required before claiming a media journey. |
| WebRTC network roaming | Call signaling includes a 15-second disconnect grace period (`CallTimeoutScheduler.java`, `disconnect-grace-ms: 15000`) and client `RECONNECTING_NETWORK` state with ICE restart (`CallManager.java`). | Transient Wi-Fi <-> LTE/5G handover within 15 seconds preserves active calls; network loss exceeding 15 seconds terminates the call. |
| Legacy inbox call preview direction | New `CALL|<END_REASON>|<durationSeconds>|<callerUserId>` rows let the inbox compare the caller with the signed-in user and render the correct direction. Older three-part rows have no caller ID and use direction-neutral wording, including for completed calls. | Direction cannot be recovered for call rows written before caller IDs were added; only new call rows display direction-aware previews. |
| Conversation summary | The summary route, extractive local engine, optional OpenAI-compatible LLM engine (tested with Gemini `gemini-3.1-flash-lite` through Gemini's OpenAI-compatible base URL), consent gate, Flyway V6 tables and Android summary UI are shipped (`docs/media/screens/stitch-06-ai-summary-sheet.png`). The local engine is extractive: it selects and labels existing messages and does not generate new prose. The LLM engine is optional and requires both an operator key and the user's `aiSummaryConsent`; without either, no text leaves the server. | Consent is account-level, with an additional per-conversation opt-out (Flyway V13): a member can exclude their own messages from external LLM input in one conversation. The built-in local extractive engine may still quote opted-out messages because no text leaves the server. A real LLM call was exercised by the live smoke script and by the device run against the live backend when configured with valid credentials. |
| Summary privacy | With consent and an operator key, the external LLM receives redacted eligible text from every participant in the window except members who opted out in that conversation; the cloud primary, cloud fallback and the local server model all receive the filtered window. | The local extractive engine may still quote an opted-out member's messages. Its output is visible only to conversation members, who can already read the source messages; this is not a disclosure to a third party. |
| Summary redaction scope | Phone, e-mail and URL redaction runs on text sent to the external LLM. The local extractive engine quotes existing messages, so a selected message that contains such a token is shown unredacted to the requester, who can already read it. | Not a disclosure to a third party. Redact the local output as well if summaries are ever exported or shared. |
| Summary consent revocation | Revoking `aiSummaryConsent` makes later requests use the local engine and no cached LLM output is served (live E2E scenario). The provider re-checks the persisted flag immediately before building the external prompt, and the opt-out rows are re-read at the same point. | A revocation or opt-out committed after request start wins the race by design; a request whose provider call is already in flight may still complete. |
| Call session retention | `CallRegistry` evicts terminal call sessions on the next registry access after five minutes; active sessions remain in memory (`server/src/main/java/com/nexachat/call/CallRegistry.java`). | The cache can include recently ended calls; persisted call rows and chat history remain available after eviction. |
| Call signaling lock | Call-control mutations share one fair lock until the database transaction completes. SDP and ICE relays hold the matching read lock for that span (`server/src/main/java/com/nexachat/call/CallService.java`). | A slow call commit can delay media frames for other calls. This fits the single-node demo and is not a concurrency-throughput claim. |
| Call persistence retry | A failed timeout or last-session disconnect history write is retried five times with exponential backoff, then stopped. A disconnect retry also stops if the user is online again (`CallTimeoutScheduler`, `CallDisconnectListener`). | A lasting database outage can leave the in-memory call reserved without a history row until restart. |
| Browser client | The supported realtime client is the native Android app using raw WebSocket + STOMP; no browser UI or SockJS fallback is provided. | There is no desktop/web messaging client. |
| Render Free tier hosting (compute & cold start) | The production backend is deployed on Render Free tier in Singapore (512 MB RAM, 0.1 vCPU). In the supported production configuration, an external uptime monitor pings `https://api.nexachat.io.vn/actuator/health/liveness` every 5 minutes, keeping Render awake 24/7 ([docs/operations/production-runbook.md](../operations/production-runbook.md)). If a container cold start occurs (e.g. after deployment or monitor failure), local benchmarking capped at 512 MB / 0.1 CPU reached readiness in 120–185 s with the AppCDS archive and 167–328 s without (readiness on Render not yet measured; the first live Render deploy without AppCDS measured 123 s from container start to healthy, with Spring Boot starting in 106.6 s). The `render.yaml` `JAVA_OPTS` block is the source of truth for production JVM flags (`MaxRAMPercentage=60.0`, `SerialGC`, C1 compilation only via `TieredStopAtLevel=1`, `512k` thread stacks, and AppCDS archive `/app/application.jsa`; `render.yaml:44-55`), overriding the image default at `server/Dockerfile:80`. | First request during an active cold start may experience elevated latency or transient HTTP 502/504 errors from the ingress reverse proxy until container readiness. The Android client detects cold starts, renders a localized waiting indicator, and retries with bounded backoff. High concurrent load risks container cgroup OOM termination (exit code 137). Operational details, keep-alive monitor setup, and secret rotation live in [docs/operations/production-runbook.md](../operations/production-runbook.md). Upgrade path: Render Starter plan ($7/mo) eliminates spin-down. |
| Neon Serverless Postgres Free tier (PG 18) | Production database runs on Neon Serverless Postgres (PostgreSQL 18) in Singapore (`ap-southeast-1`). Free tier provides 0.5 GiB (512 MB) storage and 100 compute hours/month; compute auto-suspends after 5 minutes of idle. On Render (`SPRING_PROFILES_ACTIVE=prod,render,json-logs`), HikariCP is configured via `application-render.yml:26-34` with `maximum-pool-size: 5`, `minimum-idle: 0`, and `idle-timeout: 60000` (releasing idle connections after 1 min so Neon can suspend even while Render is kept awake by liveness pings). Standalone prod defaults (`maximum-pool-size: 10`, `minimum-idle: 2`, `application-prod.yml:60-61`) apply only outside the Render profile. | First query on suspended compute adds 1–3 s latency while compute resumes. Storage exceeding 512 MB prevents further message, token, and attachment row inserts. High concurrent connection bursts risk hitting compute or connection caps; connections must use the Neon direct endpoint (not the `-pooler` endpoint, which conflicts with session advisory locks used by Flyway and ScheduledAdvisoryLock; see `render.yaml:57-59` and `docs/operations/deploy-render.md:30-34`). Upgrade path: Neon Launch tier ($19/mo). |
| Supabase Storage Free tier (1 GB / 5 GB egress) | Avatars and message attachments are stored via Supabase S3-compatible object storage. The Free tier includes 1 GB total storage and 5 GB monthly egress bandwidth. Server enforces 25 MB max upload size (`StorageService.MAX_FILE_SIZE_BYTES=25MB`). | Uploaded bytes accumulate because soft-deleted messages retain stored files. Storage exceeding 1 GB blocks new uploads; egress exceeding 5 GB throttles downloads. Operators can bound disk usage by enabling avatar sweep (`NEXACHAT_AVATAR_SWEEP_ENABLED=true`, `NEXACHAT_AVATAR_SWEEP_DRY_RUN=false`) and attachment retention cleanup (`NEXACHAT_RETENTION_ENABLED=true`, `NEXACHAT_RETENTION_DRY_RUN=false`, and `NEXACHAT_RETENTION_ATTACHMENTS_ENABLED=true`). Upgrade path: Supabase Pro tier ($25/mo). |
| Firebase Spark plan limits (RTDB & FCM) | Realtime push delivery uses FCM v1 (`fcm.googleapis.com`); ephemeral presence/typing uses optional Firebase RTDB bridge ([docs/architecture/firebase-realtime.md](../architecture/firebase-realtime.md)). Firebase Spark (free) plan permits up to 100 simultaneous RTDB connections, 1 GB storage, and 10 GB/month download. | More than 100 concurrent RTDB client connections triggers throttling. If RTDB limits are saturated, the operator engages `/control/adminDisabled` to route all clients back to STOMP over WebSocket. FCM push notifications remain free and unlimited. Upgrade path: Firebase Blaze pay-as-you-go plan. |
| Message visibility after rejoining a group | A member who is removed and added back sees only messages created from their latest admission onward, on every read surface: history, resync, search, pins, archive, attachments and realtime. Messages they sent or received in an earlier membership are not shown again. | Intentional boundary so content from the absence cannot leak; restoring earlier own messages would need a product decision and one consistent exception across all surfaces. |
| Sign-in attempt budgets | Wrong-password attempts are limited per normalized credential (email or phone) and per source address. An account that has both an email and a phone has one budget for each. | Bounded doubling of the per-account budget; the per-address limit still applies. A shared per-account budget is a possible hardening. |

## 2. Android and offline behavior

| Limitation | Current behavior | Impact / next step |
|---|---|---|
| Reaction event retention | `reaction_events` (V10) is the audit log that makes removals visible to delta sync. Rows are deleted only when `NEXACHAT_RETENTION_REACTION_EVENTS_ENABLED=true`; the delta contract still treats `nexachat.sync.reaction-retention-days` (default 30) as the partial-sync horizon. | A client offline longer than that window receives `reactionsFullRefresh=true` and must reload reactions from history; a partial delta would be incomplete. |
| Interaction actions while offline | Reactions and pins keep the optimistic local change and enqueue a durable `offline_outbox` action in the same Room transaction (`MessageRepository.java`). `OutboxSyncWorker` dispatches it with a stable idempotency key, retries transient failures with exponential backoff, and rolls back with a visible error only on a permanent 4xx. | Retry attempts are bounded; a permanent failure reverts the optimistic state. Real device/WorkManager scheduling and doze behaviour are not covered by JVM tests. |
| Attachment forwarding | Message forwarding supports live `TEXT` content only (`android/app/src/main/java/com/nexachat/core/ui/ForwardFilter.java`). | Images, audio, video, files, and deleted messages cannot be forwarded through this action. |
| Client inbox paging | The Android inbox loads 30 conversations per page (`ConversationRepository.refreshInboxPage`/`loadNextInboxPage`) and prunes local rows only after a full walk from the first page. | A very large inbox needs several scroll-triggered requests; search over unloaded pages is not available offline. |
| Deep history jump | Quote/pin jumps page at most 20 history pages (`MessageRepository.MAX_JUMP_PAGES`). | A target beyond the bound may not be reached by the jump flow. |
| Reconnect while backgrounded | `OutboxSyncWorker` (WorkManager `NetworkType.CONNECTED`) drains pending outbox messages and offline actions while backgrounded. However, the persistent STOMP WebSocket connection in `RealtimeSession` remains parked while backgrounded and re-arms on app foreground, network change broadcast, or user action (`RealtimeSession.java`). | Realtime push delivery while backgrounded requires foregrounding or external push wakeup; outbox draining executes automatically via WorkManager. |
| Data retention cleanup | `RetentionJobRunner` implements bounded cleanup for invite links, tokens, polls, attachments, tombstones, reaction events and related rows, gated by `NEXACHAT_RETENTION_*` (`server/src/main/resources/application.yml:167-222`). Cleanup requires three explicit settings: global `NEXACHAT_RETENTION_ENABLED=true`, disabling dry-run `NEXACHAT_RETENTION_DRY_RUN=false` (defaults to `true`, which counts candidates without deleting), and specific per-job flags `NEXACHAT_RETENTION_<JOB>_ENABLED=true`. Flyway `V22` adds supporting indexes. | No automatic purge runs in the default configuration or Compose demo; operators must opt in explicitly through all three settings. Reaction delta still uses `nexachat.sync.reaction-retention-days` as the partial-sync horizon whether or not purge is enabled. |
| Instrumented migration coverage | `RoomMigrationInstrumentedTest` validates exported Room transitions 6→7 through 11→12 and the full 6→13 chain (which includes 12→13); legacy v1→v7 fixtures remain in `RoomMigrationTest`. This worktree compiles the tests but does not run them on a device. | Compilation does not prove row preservation on SQLite; the lead must run the connected migration tests on the assigned emulator before accepting this coverage. |
| Play App Signing / App Links | Release builds use a local upload keystore (`tools/release/sign-release.sh`); production `https://nexachat.io.vn/.well-known/assetlinks.json` must list every signing certificate users install (upload key and, after store enrollment, the Play App Signing certificate). | Until the Play signing SHA-256 is appended, Play-distributed installs may fail Android App Link verification. Operator steps live in `docs/operations/domain-and-app-links.md` (not edited in this audit pass). |
| Android App Link verification | `autoVerify` deep links target `https://nexachat.io.vn/join/<token>` on release builds. | Domain, `assetlinks.json`, and fingerprints must stay aligned with the shipped signing keys; mismatches fall back to the browser/join page instead of direct app open. |
| Debug LAN transport | The Android `debug` and `localSmoke` source sets permit cleartext HTTP/WS for LAN demos (`android/app/src/debug/res/xml/network_security_config.xml`, `android/app/src/localSmoke/res/xml/network_security_config.xml`); release uses `src/main` with no exemptions. | Credentials and traffic can be observed on an untrusted network. Use only a trusted demo LAN; production requires HTTPS/WSS. |
| Push notifications | Client token registration (`DeviceTokenApi`, `TokenStore`, `NexaFirebaseMessagingService`, `FcmMessageProcessor`) and server OAuth2 service-account dispatch (`DefaultFcmPushService`, `GoogleHttpFcmGateway`) are implemented; however, production delivery requires an external Firebase project, server service-account JSON (`FCM_SERVICE_ACCOUNT_JSON`), and client `google-services.json` (none bundled in repository). | Real notifications are delivered only when external Firebase credentials and configuration are supplied; otherwise local mock/in-app signaling is used. |
| FCM after Android force-stop | Android does not deliver FCM data messages while the user has force-stopped the app. | FCM cannot wake the stopped app; recovery depends on a later app launch and the feature's API refresh. |
| End-to-end encryption | Transport security is TLS-dependent; message and file content is not end-to-end encrypted. | Server/database or backup access can expose stored content. Note that `demo/backup.sh` is strictly local Compose demo-scoped; hosted production requires paired database and Supabase S3 object storage recovery. |
